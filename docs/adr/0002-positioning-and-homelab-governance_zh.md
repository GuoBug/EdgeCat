## 1. 背景与核心问题 (Context)

在完成 EdgeCat 基础流式治理内核后，项目面临向 Personal AI（个人与边缘常驻 AI）演进的三个核心架构抉择：
1. **品类定位**：EdgeCat 应该保持为纯粹的“本地优先推理治理网关”，还是扩张为内置长期记忆、定时队列与管理 UI 的“个人 AI 中枢（Personal AI Hub）”？
2. **共享与联动边界**：当与前端工作流编排器（如 **PatchCat**）或家里/工作室的多台客户端联动时，如何管理云端主 API Key 的安全边界？是否支持公网共享？
3. **隐私与持久化的物理冲突**：当前的 PII `Vault` 是单次请求生命周期的内存映射（`{{EC_PII_PHONE_1}}`）。若引入跨会话持久化或记忆检索，如何在不破坏 `CGO_ENABLED=0` 纯静态编译的前提下处理隐私与全文检索的冲突？

---

## 2. 决策一：网关是本体，中枢是用法，不是品类 (Gateway as Core, Hub as Usage)

- **结论**：**坚定守住“本地优先的确定性流式治理网关（Local-First AI Inference Governance Gateway）”本体，拒绝膨胀为重型纵向中枢产品。**
- **工程与竞争集考量**：
  1. **横切关注点 vs. 纵向产品**：网关解决的是横切基础设施痛点（TTFT 首字超时静默降级、SSE 跨分包 PII 占位符拼合还原、协议无损透传、无锁 WAL 审计），这套原语对个人极客、家庭 NAS 与企业边缘节点完全通用；而“AI 中枢”强绑定特定 UI、安装器与业务假设，会稀释最硬核的流式治理工程信号。
  2. **扩展方式**：任何有状态的增强能力（如上下文/记忆注入），未来仅作为 `RequestMutator` 扩展接口的轻量插件示例（Dogfooding 扩展点），而不作为网关的核心包袱。

---

## 3. 决策二：聚焦“家庭 / 小团队内网共享 (Homelab & Studio LAN)”，拒绝公网多租户

在部署形态上，排除“公网暴露共享运行时”的伪需求，确立 **单机 Localhost** 与 **家庭/小团队内网（NAS / Homelab）共享** 两种标准模式：

| 维度 | 公网多租户网关 (明确不做) | 家庭 / 小团队内网共享 (核心支持场景) |
| :--- | :--- | :--- |
| **典型拓扑** | 暴露公网域名供陌生人调用 | 1 台家庭 NAS / Mac mini / 软路由常驻 EdgeCat，家里或工作室 2~3 人、多台设备（PC / 手机 / PatchCat）局域网共用 |
| **核心价值** | 复杂计费、防 DDoS、企业 RBAC | **统一托管主 API Key、统一本地 7B 白嫖与云端保底、统一隐私出网拦截、统一分账审计、省多份订阅费** |
| **工作流分享单位** | 分享运行时端点（谁分享谁破产） | **分享工作流定义（PatchCat 导出不含 Key 的 DAG JSON）**，接收方导入后连接各自内网的 EdgeCat |

### 网关托管 Key 的真实安全模型：
将云端主 API Key 收归 NAS 上的 EdgeCat 配置文件，并不意味着前端绝对免受 XSS 影响（前端仍需在 `localStorage` 保存访问 EdgeCat 的子令牌）。真正的工程安全增益来自三道防线：
1. **主 Key 零暴露与子令牌随时可撤销（Revocable Sub-Tokens）**：按设备签发子令牌（如 `ec-workstation`、`ec-ipad`），泄露时修改配置即可吊销，无需轮换上游云厂商主密钥。
2. **本地免费不限流，云端降级硬配额（Daily Cloud Fallback Quota）**：白嫖本地 Ollama 算力不设限；一旦触发向付费 Cloud Tier 降级，按子令牌执行每日云端调用配额熔断，彻底杜绝前端 XSS 或 Agent 死循环刷爆云端账单。
3. **Fail-Closed 局域网门卫**：默认监听 `127.0.0.1`；当配置为 `0.0.0.0` 或局域网 IP 供内网共享时，强制要求启用子令牌鉴权与受控 CORS 白名单（含 Chrome PNA `Access-Control-Allow-Private-Network: true`），拒绝内网无鉴权裸奔。
   > ⚠️ **实施状态**：本条为已确立的决策方向，对应 R2.1（P0，Phase 2）。**当前代码默认仍为 `0.0.0.0` 且尚未接入入站鉴权**，因此现阶段只应运行在可信局域网内，切勿直接暴露公网。

## 4. 决策三：威胁模型与存储分层（为什么不做全库加密 SQLCipher）

针对“是否需要将 SQLite 全库加密以支持持久化记忆/PII”的讨论，经底层核验确立以下硬约束：

1. **全库加密与 `CGO_ENABLED=0` 及 FTS5 物理互斥**：
   - `modernc.org/sqlite` 为纯 Go 实现，不支持 SQLCipher；引入 SQLCipher 必须退回 `mattn/go-sqlite3`（依赖 CGO），直接摧毁单二进制跨平台静态编译能力。
   - SQLite FTS5 全文检索依赖明文 Token 索引，全库密文下无法建立有效索引（且中文环境必须显式开启 `tokenize='trigram'`）。
2. **明确的威胁模型（防离线副本泄露，而非防本机 Root 攻击者）**：
   - 在单机或家庭 NAS 场景下，若攻击者已具备读取宿主机进程内存或 OS Keyring 的权限，任何本地加密均形同虚设。加密的真实意义仅在于防止**数据库文件随网盘同步、备份盘或设备送修发生离线副本泄露**。
3. **存储分层准则**：
   - **默认基线（当前生效）**：PII `Vault` 保持 **100% 纯内存、单请求即焚（Per-Request Ephemeral Vault）**；`audit_logs` 仅记录脱敏计数、路由去向与延迟指标，**绝不落盘原始对话内容与敏感词明文**。（按客户端维度归因的 `client_name` 列属 R2.5 规划，当前 schema 中尚不存在。）
   - **未来可选记忆插件契约（Phase 3 预留）**：若后续作为插件引入跨会话记忆，必须遵循三层分离——短期对话带 TTL 滚动清理、长期记忆仅存本地模型蒸馏后的**脱敏事实（Distilled Non-PII Facts）**、跨请求占位符必须将自增序号升级为 `HMAC-SHA256(原文, 本地密钥)` 稳定键。

## 5. 决策影响评估 (Consequences)

### 积极影响：
- **架构极度克制且自洽**：用约 12MB（`linux/amd64`，`-s -w` 静态编译）的纯静态单二进制，精准吃透“个人极客本机 + 家庭/工作室 NAS 局域网共享”场景，无需背负重型 UI 与多租户计费包袱。
- **消除协议与流式隐患**：通过 `internal/proxy/protocol.go` 实现请求/响应无损透传（完整保留 `tools`、`tool_calls`、`reasoning_content` 与多模态数组），并通过 `stream_idle_timeout_ms` 滚动写超时解决本地慢速模型长流断连问题。

### 代价与边界说明：
- EdgeCat 不是公网 API 分发系统，严禁在未挂载 TLS 反向代理与鉴权的情况下直接暴露于公网（已在文档与配置中明确声明）。
